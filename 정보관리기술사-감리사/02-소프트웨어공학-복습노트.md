## 1. 개발 흐름과 요구사항

**요구사항 → 설계 → 구현 → 테스트**

요구사항은 무엇을 만들고 어떤 조건을 만족해야 하는지를 합의한 기준이다. 설계는 이를 실현할 구조와 처리 흐름을 정하고, 구현은 설계를 코드로 옮기며, 테스트는 요구사항을 충족하는지 확인한다.

실제 개발에서는 이 과정을 반복할 수 있지만, 요구사항과 설계·구현·검증의 연결은 유지되어야 한다.

### 요구사항의 네 가지 품질

> **암기:** 명확성 · 완전성 · 일관성 · 검증 가능성

- **명확성:** 여러 사람이 같은 의미로 이해할 수 있다.
- **완전성:** 합의한 범위에서 필요한 조건과 정상·실패·예외 흐름이 빠지지 않는다.
- **일관성:** 요구사항끼리 모순되지 않는다.
- **검증 가능성:** 충족 여부를 판정할 방법과 기준이 있다.

**예시 — “검색 결과가 빨라야 한다”를 개선하기**

“빠르다”는 사람마다 기준이 달라 모호하다. 다음처럼 측정 조건과 판정 기준을 함께 정하면 검증하기 쉬워진다.

> 지정한 시험 환경에서 동시 사용자 100명, 주문 데이터 100만 건으로 10분간 정해진 조회 시나리오를 수행할 때, 요청의 95%가 2초 이내에 응답해야 한다.

숫자만 붙이는 것으로 충분하지 않다. 어떤 환경과 부하에서 무엇을 측정할지도 정해야 한다.

### 성공 조건과 실패 조건을 함께 검증하기

**요구사항:** 결제 성공 시 주문을 확정하고, 성공하지 않은 경우에는 주문을 확정하지 않는다.

- 결제 성공 → 주문 확정 여부를 확인한다.
- 결제 실패 → 주문 미확정 여부를 확인한다.

결제 결과와 무관하게 모든 주문을 확정하는 잘못된 프로그램도 성공 테스트는 통과할 수 있다. 따라서 **성공 테스트만으로 요구사항 전체를 검증했다고 볼 수 없다.**

엄밀히 “성공한 경우에만 확정한다”는 확정하려면 성공해야 한다는 필요조건을 뜻한다. 성공 시 확정까지 보장하려면 두 방향을 분명하게 적는다.

“데이터 무결성을 확인한다”는 추상적인 표현도 이 사례에서는 **“결제 실패인데 주문은 확정된 모순된 상태가 생기지 않는지 확인한다”**로 구체화할 수 있다.

## 2. 추적성과 변경 영향 분석

### 요구사항 추적성

> **암기:** 요구사항의 출처와 관련 설계·구현·테스트를 연결해 **누락과 변경 영향**을 확인할 수 있는 성질이다.

요구사항 R-01에 설계 D-01과 테스트 T-01·T-02를 연결하면 필요한 설계나 테스트가 빠졌는지 찾을 수 있다. 요구사항이 바뀔 때 무엇을 수정하고 재검증할지도 파악할 수 있다.

추적성의 두 목적은 **① 구현·검증 누락 점검, ② 변경 영향 분석**이다.

**주의:** 추적표에 테스트가 연결됐다는 사실만으로 검증이 충분한 것은 아니다. 연결된 테스트가 정상·실패·예외 조건을 실제로 확인하는지까지 검토해야 한다.

### 변경 영향 분석

> **암기:** 변경에 영향을 받는 대상을 찾아 **수정·재검증 범위**를 정하는 활동이다.

취소 가능 시간을 결제 후 30분에서 10분으로 바꾸면 다음 대상을 검토한다.

- 코드와 관련 설정
- 요구사항 명세서, 관련 설계, 사용자 안내
- 테스트 케이스와 기대 결과

기존의 “15분 후 취소 허용” 테스트는 변경 후 **거절**을 기대하도록 바꿔야 한다.

인프라 문서는 인프라 구성이나 설정에도 영향이 있을 때 수정한다. 모든 문서를 일괄 수정하는 것이 아니라, 영향을 분석해 실제 수정 대상을 결정한다.

## 3. 경계값 테스트

> **암기:** 허용과 거절 등이 갈리는 **경계 부근**을 확인하는 방법이다.

**조건:** 결제 완료 시각부터 경과 시간이 10분 이하일 때만 취소를 허용한다.

| 취소 요청 시점 | 기대 결과 |
|---|---|
| 9분 59초 | 허용 |
| 정확히 10분 | 허용 |
| 10분 1초 | 거절 |

“이하”는 경계를 포함하므로 판단식은 `경과 시간 ≤ 10분`이다.

**경계 직전 · 경계 · 경계 직후**를 확인하면 `<`와 `<=`를 잘못 쓰는 오류 등을 발견하는 데 도움이 된다. 감리에서는 이런 테스트의 존재뿐 아니라 실제 수행 결과도 확인한다.

## 4. 상태 설계와 시퀀스 설계

> **암기:** 상태는 대상의 **현재 상황**, 상태 전이는 사건이나 조건에 따른 **상태 변화**다.

- **상태 다이어그램:** 어떤 상태 변화가 가능한지 보여준다.
- **시퀀스 다이어그램:** 여러 참여자가 어떤 메시지를 어떤 순서로 주고받는지 보여준다.

시퀀스에서는 참여자의 생명선과 메시지 순서를 읽는다. `alt`는 조건에 따른 대안 흐름을 나타내며, Python의 `if / elif / else`와 비교할 수 있다.

**예시 — 설계 산출물 간 일관성**

상태 설계에서 취소 완료 후 배송 시작을 금지했는데, 시퀀스에는 취소 완료 후 물류 서비스로 배송 시작 요청을 보내도록 되어 있다면 두 설계가 불일치한다.

두 산출물은 같은 업무 규칙을 따라야 한다. 각 문서를 따로 보는 데 더해, **같은 요구사항을 서로 모순 없이 표현했는지** 연결해서 검토한다.

## 5. 타임아웃과 결제 결과 확인

> **암기:** 타임아웃은 정해진 시간 안에 **응답을 받지 못한 것**이며, 결제 실패가 확정됐다는 뜻은 아니다.

결제 제공자에서는 결제가 성공했지만 응답만 유실됐을 수 있다. 이를 곧바로 실패로 판단해 새로운 결제를 시도하면 **중복 청구 위험**이 생긴다.

타임아웃 이후의 처리 흐름은 다음과 같다.

1. 결제를 **결과 확인 중**으로 관리한다.
2. 기존 거래의 결과를 조회한다.
3. 조회 결과에서 **결제 성공이 확인되면** 주문을 확정한다.
4. 최종 실패가 확인되면 확정하지 않는다. 계속 불명확하면 확인 중 상태를 유지하면서 후속 조회·운영 확인 정책으로 해결한다.

**주의 — 조회 성공과 결제 성공은 다르다.**

조회 요청이 정상 처리됐어도 반환된 결제 상태는 실패일 수 있다. 주문 확정 조건은 **조회가 됐다는 사실이 아니라, 해당 거래의 결제 성공이 확인됐다는 사실**이다.

## 6. 멱등성과 중복 처리 방지

> **암기:** 멱등성은 동일한 연산을 여러 번 적용해도 **한 번 적용한 것과 결과가 같은 성질**이다.

결제에서는 같은 결제 시도가 반복 전송돼도 실제 결제가 추가로 발생하지 않게 하는 데 적용한다.

**같은 시도의 재전송 → 같은 멱등성 키 사용 → 서버에서 중복 실행 통제**

서버는 해당 키의 처리 상태·결과를 관리해야 한다. 이미 처리 중이거나 완료된 요청에는 추가 결제 없이 기존 상태·결과를 반환하는 방식으로 처리할 수 있다. 동시 요청도 중복 실행되지 않도록 통제하며, 실제 연동은 결제 제공자의 규약에 맞춰 설계한다.

### 식별키를 부여하는 것만으로는 부족하다

키는 같은 요청을 구별하는 수단이다. **키를 부여하기만 해서는 멱등성이 보장되지 않으며, 그 키로 중복 실행을 막는 처리가 필요하다.**

같은 고객이 같은 상품을 같은 금액으로 별도 구매했다면 각각 다른 구매이므로 중복으로 차단하면 안 된다. 주문 식별자, 거래 조회용 식별자, 멱등성 키도 반드시 같은 값인 것은 아니다.

결제 중복 방지와 함께 **주문 확정 처리의 중복**도 막아야 한다. 성공 응답을 두 번 받았다고 재고를 두 번 차감해서는 안 된다.

**서술 연습:** “멱등성을 보장한다”라는 목표에 **같은 시도의 같은 키 재사용과 서버의 중복 실행 통제**라는 방법까지 붙이면 구체적인 설명이 된다.

## 7. 구현 방안과 감리 확인 자료

> **암기:** 구현 방안은 **어떻게 만들 것인가**, 확인 자료는 **실제로 동작했음을 무엇으로 확인할 것인가**에 해당한다.

| 구분 | 예시 |
|---|---|
| 구현 방안 | 식별키 도입, 중복 처리 통제 |
| 확인 자료 | 테스트 케이스·수행 결과, 결제 거래 내역, 주문 상태 이력 |

식별자는 관련 기록을 연결하는 데 활용할 수 있지만, 키의 존재만으로 올바른 동작이 입증되지는 않는다.

**예시:** 결제 실패 상황의 테스트 수행 결과와 관련 기록을 대조하여 주문이 미확정으로 남았는지 확인한다.

## 8. 상태 전이 테스트와 커버리지

### 불허 전이 테스트

> **암기:** 금지된 상태 변경을 일부러 요청하고 **시스템이 차단하는지** 확인하는 테스트다.

취소 완료 주문에 배송 시작 처리를 요청하는 경우를 다음처럼 정리한다.

- **사전 조건:** 주문 취소가 완료되어 있다.
- **수행:** 주문 서비스에 배송 시작 처리를 요청한다.
- **기대 결과:** 요청 거절, 취소 완료 상태 유지, 물류 서비스로 신규 배송 요청 미전송.

**요청이 거절되어야 테스트가 통과한다.** 응답에서 “배송 불가”라고 했더라도 실제 물류 서비스에 배송 요청이 전송됐다면 테스트는 실패다.

이번 규칙의 기준은 **주문 취소 완료 상태**다. 결제 취소·환불 상태는 별도로 관리될 수 있다.

### 상태 커버리지와 전이 커버리지

- **상태 커버리지:** 모델의 상태를 얼마나 방문했는지 나타낸다.
- **전이 커버리지:** 상태 변화들을 얼마나 실행했는지 나타낸다. 이번 예시에서는 허용 전이를 기준으로 센다.

**예시 — 상태를 모두 방문해도 빠진 전이가 있을 수 있다.**

| 테스트 | 경로 |
|---|---|
| T1 | 결제 대기 → 결제 완료 → 배송 중 |
| T2 | 결제 대기 → 취소 완료 |
| T3 | 결제 대기 → 결제 완료 → 취소 완료 |

T1과 T2만으로 상태 4개는 모두 방문하지만, **결제 완료 → 취소 완료** 전이가 빠진다. T3를 추가하면 모델의 허용 전이 4개를 모두 다루도록 구성할 수 있다.

허용 전이 검증과 불허 전이 시도에 대한 거절 검증은 구분한다. 전이를 모두 다뤘다고 모든 조건·경로·오류까지 검증한 것은 아니다.

## 9. 테스트의 목적과 수준

### 목적: 확인 테스트와 회귀 테스트

> **암기:** 확인은 **해당 결함의 수정 검증**, 회귀는 **변경 후 기존 동작의 유지 검증**이다.

| 목적 | 확인할 내용 | 배송 결함 수정 사례 |
|---|---|---|
| 확인 테스트 | 발견한 결함이 수정됐는지 | 취소 완료 주문의 배송 요청이 실제로 차단되는지 |
| 회귀 테스트 | 변경으로 기존 기능에 결함이 생기지 않았는지 | 정상 주문의 배송까지 막히지 않았는지 |

취소 완료 주문의 배송을 막도록 수정하다가 모든 주문의 배송을 막아버릴 수도 있다. 따라서 해당 결함의 수정 여부와 기존 정상 동작의 유지 여부를 함께 살핀다.

### 수준: 단위·통합·시스템·인수

> **암기:** 수준은 **검증 대상·범위**, 목적은 **검사하는 이유**다.

| 대표적인 수준 | 검증 대상·초점 |
|---|---|
| 단위 | 작은 함수나 모듈 |
| 통합 | 구성요소 사이의 인터페이스와 상호작용 |
| 시스템 | 전체 시스템의 기능·품질 |
| 인수 | 업무 필요와 합의한 수용 기준 충족 여부 |

인수 테스트를 반드시 고객만 실행하는 것은 아니다. 확인·회귀는 수준과 별개의 목적이므로 한 테스트를 두 기준으로 설명할 수 있다.

**조합 예시**

- 할인 계산 함수의 기존 동작 재검사 → **단위 수준 + 회귀 목적**
- 결제 모듈 수정 후 기존 주문 모듈과 요청·응답이 정상 유지되는지 재검사 → **통합 수준 + 회귀 목적**

## 10. 회귀 테스트 대상 선정

> **암기:** 변경의 **직접·간접 영향**을 분석하고, **결함 발생 가능성과 피해 규모**로 우선순위를 정한다.

수정한 함수를 직접 사용하는 기능뿐 아니라, 그 결과 데이터나 연결된 인터페이스를 사용하는 후속 기능도 살핀다.

**예시 — 코드가 바뀌지 않은 기능에도 영향이 갈 수 있다.**

**할인 계산 함수 → 최종 결제 금액 → 환불 금액**

할인 계산 함수의 변경이 최종 결제 금액에 반영되고 환불이 그 금액을 참조한다면, 환불 코드가 바뀌지 않아도 전체 환불 흐름의 금액 정합성에 영향이 갈 수 있다. 따라서 코드 수정 여부만으로 검토 범위를 결정하지 않는다.

> **학습 상태:** 간접 영향 개념은 설명까지 접한 상태다. 마지막 적용 문제는 아직 답하지 않아 **미응답·보류**로 남겨두었다.

## 복습할 때 다시 구분할 것

먼저 각 절의 암기 문장을 가리고 본인 말로 설명한 뒤, 같은 개념을 주문·결제 사례에 적용해 본다.

- **성공 테스트만으로 부족한 이유:** 실패·예외 상황의 검증이 빠질 수 있다.
- **추적성의 두 목적:** 구현·검증 누락 점검과 변경 영향 분석.
- **타임아웃과 실패:** 응답 미수신과 결제 실패 확정은 다르다.
- **식별키와 멱등성:** 같은 키 사용에 더해 중복 실행 통제가 필요하다.
- **구현 방안과 확인 자료:** 통제 방법과 실제 동작을 확인할 증거를 구분한다.
- **불허 요청과 테스트 판정:** 기대한 거절·상태 유지·금지된 후속 동작 미발생이 확인되면 통과다.
- **확인과 회귀:** 해당 결함 수정과 기존 동작 유지를 구분한다.
- **수준과 목적:** 한 테스트를 통합 수준이면서 회귀 목적이라고 설명할 수 있다.

용어를 적은 뒤 **어떤 위험을 막는지 → 무엇으로 검증하는지**까지 이어 쓰는 연습이 기술사식 서술과 감리 판단을 함께 준비하는 방법이다.
