# 테스트와 보안

[[00-학습-허브]] · [[06-오답-복습]] · [[08-소프트웨어-설계]]

## 테스트의 범위와 관점

| 테스트 | 확인하는 것 | 예 |
|---|---|---|
| **단위(유닛)** | 함수·모듈 등 작은 단위 | 할인 계산 함수 하나 |
| **통합** | 구성요소·시스템 사이 인터페이스와 상호작용 | 주문 모듈과 결제 모듈의 요청·응답 데이터 교환 |
| **시스템** | 전체 시스템이 명세된 기능·품질을 충족하는지 | 쇼핑몰 전체 주문 흐름·성능 확인 |
| **인수** | 업무 필요·합의한 수용 기준 충족 여부 | 고객과 합의한 업무 시나리오·수용 기준 검증 |

| 관점 | 기준 |
|---|---|
| **블랙박스** | 내부 코드를 보지 않고 입력과 출력, 요구사항으로 검사 |
| **화이트박스** | 코드의 내부 구조·경로 등을 살펴 검사 |

단위·통합·시스템·인수는 대표적인 테스트 수준 분류다. 통합은 구성요소 간 통합과 시스템 간 통합 등으로 더 나눌 수 있다. 인수는 업무 필요·수용 기준에 초점을 두며 반드시 고객만 실행한다는 뜻은 아니다. 수준별 테스트가 항상 엄격히 순차 실행되는 것은 아니다. 블랙박스·화이트박스는 어떤 정보를 보고 검사하는가라는 관점이므로 단위 테스트도 블랙박스 관점으로 설계할 수 있다.

## 확인 테스트와 회귀 테스트

| 구분 | 목적 | 배송 결함 수정 사례 |
|---|---|---|
| 확인 테스트(재테스트) | 발견한 결함이 수정됐는지 확인 | 취소 완료 주문의 배송 시작 요청이 차단되고 실제 배송 요청도 전송되지 않는지 확인 |
| 회귀 테스트 | 변경으로 기존 기능에 결함이 생기지 않았는지 확인 | 결제 완료 주문의 정상 배송 시작이 계속 가능한지 확인 |

예를 들어 취소 완료 주문의 배송을 막도록 고치면서 모든 주문의 배송을 막는 결함이 생길 수 있다. 기존 결함의 수정 확인에 더해 변경 영향 분석으로 관련 기존 기능의 재검증 범위를 선정한다. 회귀는 단위·통합 같은 테스트 수준이 아니라 목적이며 여러 수준에서 수행할 수 있다. 같은 테스트가 여러 목적에 활용될 수도 있으므로 목적에 따라 구분한다.

### 수준과 목적의 조합

수준은 검증 대상·범위를, 확인·회귀 같은 목적은 검사하는 이유를 구분한다. 따라서 하나의 테스트를 두 기준으로 함께 설명할 수 있다. 할인 계산 함수 수정 후 기존 계산 동작을 다시 검사하면 단위 수준이면서 회귀 목적이다. 주문·결제 모듈의 인터페이스 재검사도 변경 후 기존 연동 유지가 목적이면 통합 수준+회귀 목적이다. 앞서 발견한 특정 연동 결함의 수정 여부를 확인하는 경우에는 통합 수준+확인 목적이 될 수 있다.

## 변경 영향에 따른 회귀 테스트 대상 선정

변경 영향 분석으로 후보를 찾고 결함 발생 가능성과 피해 규모를 고려해 우선순위를 정한다. 수정한 코드만 검사하는 것이 아니라 다음 연결을 살핀다.

- 직접 영향: 수정한 함수·모듈을 호출하는 기존 기능.
- 간접 영향: 연결된 인터페이스나 변경 결과 데이터를 사용하는 후속 기능.
- 위험: 금전 손실·보안 침해·업무 중단 등 실패의 영향과 결함 발생 가능성. 공통 코드 사용 범위·복잡성·과거 결함 등은 판단 근거가 될 수 있다.

예: 할인 계산 함수의 성능 개선에서 할인 규칙은 유지하더라도 계산 오류가 새로 생기면 최종 결제 금액이 틀릴 수 있다. 환불이 저장된 최종 결제 금액을 참조한다면 환불 코드가 바뀌지 않아도 전체 환불 흐름의 금액 정합성에 영향이 갈 수 있다. 회귀 검토 범위는 코드 수정 여부만으로 정하지 않고 데이터 의존 관계까지 분석한다. 특정 테스트를 반드시 모두 수행해야 한다는 뜻이 아니라 영향·위험 근거로 선택·우선순위를 판단한다.

## 최소 권한 원칙

사용자와 프로그램에는 **업무 수행에 필요한 권한만** 부여한다. 모든 사용자에게 관리자 권한을 주는 것은 이 원칙에 맞지 않는다.

## 비밀번호 저장

```text
Base64 인코딩 → 원래 값으로 되돌릴 수 있음 → 비밀번호 보호 수단 아님
비밀번호용 해시 + 사용자별 고유 솔트 → 검증용 값을 저장
```

같은 비밀번호라도 **사용자별 솔트가 다르면 저장된 해시도 달라진다.** 실제 비밀번호 저장에는 작업 비용을 조절할 수 있는 **비밀번호 전용 해시 알고리즘**(예: Argon2id, scrypt, bcrypt)을 사용한다. 일반적인 빠른 해시를 한 번 적용하거나 Base64로 인코딩하는 방식은 적절하지 않다.
