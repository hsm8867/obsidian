# 2026-11-05

## 학습과 확인 결과

- [[../08-소프트웨어-설계|소프트웨어 설계]]의 요구사항 추적성 서술 연습: 사용자는 요구사항의 구현 여부와 예외·에러 케이스를 포함한 테스트 필요성을 설명했다. 구현·검증 누락을 확인해야 한다는 취지는 확인했다. 변경 영향 관점과 산출물 연결이라는 추적성의 수단은 답변에 명시하지 않았다.
- 요구사항과 설계·구현·테스트의 연결을 통해 구현·검증 누락을 점검하고, 변경 시 수정·재검증 대상을 식별한다는 두 문장 답안으로 보완했다. 추적성은 테스트 수행 자체가 아니며 연결만으로 테스트의 충분성이나 품질이 보장되는 것은 아님을 설명했다.
- 주문 취소 시간 변경 사례에서 사용자는 코드 외에 요구사항 명세서·테스트 케이스·인프라 문서의 수정을 제안했다. 명세서·테스트 수정 필요성은 확인했다. 인프라 문서는 구성·설정에 영향이 있을 때 수정한다는 조건을 보완했다.
- 변경 영향 분석은 모든 문서를 일괄 수정하는 것이 아니라, 연결된 산출물을 검토해 실제 수정 대상을 정하는 것임을 설명했다. 취소 가능 시간이 바뀌면 15분 후 취소 테스트의 기대 결과도 바뀐다는 예를 들었다.
- 경계값 테스트에서 사용자는 9분 59초 허용·정확히 10분 허용·10분 1초 거절을 모두 맞혔다. 이번 사례에서 “이하”의 경계 포함 여부를 적용했음을 확인했다. 감리에서는 경계값 테스트 케이스와 실제 수행 결과를 함께 확인함을 설명했다.
- 요구사항을 상태 설계로 연결했다. 결제 처리 중에서 성공 확인·최종 실패 확인·타임아웃에 따라 상태가 달라지는 예를 소개했다. 타임아웃은 정해진 시간 내 응답을 받지 못한 것이며 결제 실패 확정을 뜻하지 않음을 설명했다.
- 타임아웃 후 새 결제 시도의 위험 질문에 사용자는 중복 결제가 발생할 수 있다고 정확히 답했다. 이번 사례에서 응답 유실 후 재결제의 위험을 확인했다.
- 타임아웃 시 결과 확인 중 상태 유지→기존 결제 식별자로 결과 조회→성공 확인 후 주문 확정 흐름을 설명했다. 최종 실패가 확인되면 미확정 처리하고, 계속 불명확하면 후속 조회·운영 확인 정책을 적용한다. 동일 시도 재전송은 제공자 규약에 따라 같은 멱등성 키를 사용하며, 주문 확정 처리의 중복도 방지해야 함을 보완했다.
- 종합 서술에서 사용자는 결과 불명확 시 대기 상태 관리, 결제 식별키 기반 상태 관리, 성공 확인 후 주문 확정을 설명했다. 기존 거래 결과 조회와 동일 시도 재전송 시 키 재사용·중복 실행 방지 방식은 명시하지 않았다. “멱등성을 보장한다” 정도의 언급이면 되는지 질문했다.
- 답안 보완: 멱등성이라는 목표에 동일 시도의 같은 키 재사용과 서버의 중복 처리 통제라는 방법을 함께 적도록 설명했다. 식별키 부여만으로 멱등성이 보장되지 않으며, 이미 처리된 요청에는 추가 결제 없이 기존 상태·결과를 반환하도록 함을 설명했다. 결과 확인 중과 최종 실패 상태는 구분하고 기존 거래의 결과 조회도 명시하도록 예시 답안을 제공했다.
- 사용자는 멱등성 설명을 이해했다고 말하고 다음 내용을 요청했다. 이를 숙달 확인으로 간주하지 않는다.
- 시퀀스 다이어그램에서 참여자·생명선·메시지 순서·요청/응답·alt 분기를 설명했다. 타임아웃→기존 거래 조회→성공/최종 실패/불명확 결과별 처리 그림을 제공했다. 결제 상태와 주문 상태, 조회 식별자와 멱등성 키, 타임아웃과 실패 응답을 구분했다.
- 시퀀스 검토에서 사용자는 조회 실패에도 주문이 확정될 위험, 조회 성공 시에만 확정하도록 순서 변경, 확인 자료로 멱등성 키 도입을 제안했다. 위험 방향은 맞다. “조회 성공”은 “조회 결과에서 결제 성공 확인”으로 표현을 명확히 했으며 실제 개념 혼동으로 단정하지 않았다.
- 확인 자료 대신 구현 방안을 제시한 점을 보완했다. 식별키는 요청·기록 연결에 쓰는 수단이고, 실제 동작의 증거는 테스트 케이스·수행 결과와 결제 거래 내역·주문 상태 이력임을 설명했다. 조회는 정상 처리돼도 반환된 결제 상태가 실패라면 주문을 확정하지 않는 예를 제시했다.
- 후속 확인에서 사용자는 결제 실패이면 주문을 확정하면 안 되며 테스트 수행 결과로 실패 시 주문 미확정 여부를 검증한다고 정확히 답했다. 이번 사례에서 결제 상태에 따른 판단과 구현 검증 자료를 구별했음을 확인했다. 간격을 두고 복습한다.
- 설계 산출물 간 일관성을 소개했다. 상태 설계가 허용하는 변화와 시퀀스의 메시지·처리 흐름이 같은 업무 규칙을 지켜야 함을 설명했다. 새 사례의 규칙은 “취소 완료 주문은 새로 배송을 시작할 수 없다”이다.
- 다음 질문: 취소 완료 후 물류 서비스에 배송 시작을 요청하는 시퀀스의 설계 불일치와, 이를 검증할 테스트 하나를 설명한다. 응답 대기이며 산출물 간 일관성 적용은 아직 확인하지 않았다.
