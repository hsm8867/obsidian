# 2026-11-05

## 학습과 확인 결과

- [[../08-소프트웨어-설계|소프트웨어 설계]]의 요구사항 추적성 서술 연습: 사용자는 요구사항의 구현 여부와 예외·에러 케이스를 포함한 테스트 필요성을 설명했다. 구현·검증 누락을 확인해야 한다는 취지는 확인했다. 변경 영향 관점과 산출물 연결이라는 추적성의 수단은 답변에 명시하지 않았다.
- 요구사항과 설계·구현·테스트의 연결을 통해 구현·검증 누락을 점검하고, 변경 시 수정·재검증 대상을 식별한다는 두 문장 답안으로 보완했다. 추적성은 테스트 수행 자체가 아니며 연결만으로 테스트의 충분성이나 품질이 보장되는 것은 아님을 설명했다.
- 주문 취소 시간 변경 사례에서 사용자는 코드 외에 요구사항 명세서·테스트 케이스·인프라 문서의 수정을 제안했다. 명세서·테스트 수정 필요성은 확인했다. 인프라 문서는 구성·설정에 영향이 있을 때 수정한다는 조건을 보완했다.
- 변경 영향 분석은 모든 문서를 일괄 수정하는 것이 아니라, 연결된 산출물을 검토해 실제 수정 대상을 정하는 것임을 설명했다. 취소 가능 시간이 바뀌면 15분 후 취소 테스트의 기대 결과도 바뀐다는 예를 들었다.
- 경계값 테스트에서 사용자는 9분 59초 허용·정확히 10분 허용·10분 1초 거절을 모두 맞혔다. 이번 사례에서 “이하”의 경계 포함 여부를 적용했음을 확인했다. 감리에서는 경계값 테스트 케이스와 실제 수행 결과를 함께 확인함을 설명했다.
- 요구사항을 상태 설계로 연결했다. 결제 처리 중에서 성공 확인·최종 실패 확인·타임아웃에 따라 상태가 달라지는 예를 소개했다. 타임아웃은 정해진 시간 내 응답을 받지 못한 것이며 결제 실패 확정을 뜻하지 않음을 설명했다.
- 타임아웃 후 새 결제 시도의 위험 질문에 사용자는 중복 결제가 발생할 수 있다고 정확히 답했다. 이번 사례에서 응답 유실 후 재결제의 위험을 확인했다.
- 타임아웃 시 결과 확인 중 상태 유지→기존 결제 식별자로 결과 조회→성공 확인 후 주문 확정 흐름을 설명했다. 최종 실패가 확인되면 미확정 처리하고, 계속 불명확하면 후속 조회·운영 확인 정책을 적용한다. 동일 시도 재전송은 제공자 규약에 따라 같은 멱등성 키를 사용하며, 주문 확정 처리의 중복도 방지해야 함을 보완했다.
- 다음 질문: 결제 타임아웃 시 중복 결제를 예방하는 처리 방안을 결과 확인·멱등성·주문 확정 조건을 포함해 2~3문장으로 설명한다. 응답 대기이며 종합 서술은 아직 확인하지 않았다.
